# 验收清单（AC）规范（单一来源）

> 被 eo-change / eo-implement / eo-test / eo-review / eo-fix 引用。AC 是 v2 验收驱动的核心工件：spec 移除后，**AC 就是「期望行为」的唯一声明**。

## 三重身份

1. **eo-implement 的完成判据**：TODO 全勾 + **auto-light** AC 验证通过 = 实施完成——**不等于验收完成**：auto-heavy 归 /eo-test，manual 可迟至 archive 硬门确认（`status: reviewed` 仅表示代码审查通过，可能仍待人工验收；未确认归档需用户显式豁免）。
2. **eo-review 的检查表**：逐条核对实现是否覆盖。
3. **eo-fix 取证时的最优书面证据**：语义分歧取证的证据瀑布（用户口述 > AC > state 意图佐证 > git 归属）中，AC 是书面期望的第一来源——但不是必要条件，无 AC 覆盖的行为按瀑布降级取证。

## 三级验证归属（auto-light / auto-heavy / manual）

分的是**「谁在哪个阶段勾」**。三方勾选权互不重叠——不重叠，同一件事就不会被两个阶段各跑一遍。

| 归属 | 判据 | 勾选权 | 阶段 |
|------|------|--------|------|
| **auto-light**（默认） | 不起环境即可验：typecheck / lint / 单测 / 静态扫描 / 单次冒烟 | eo-implement | 批末 checkpoint |
| **auto-heavy** | 要起环境：起服务、多环境组合、浏览器点击流 | **eo-test** | 一次跑完 |
| **manual** | 只有人能判（观感、手感、文案语感、体验预期），验证方式以 **「人工:」** 开头标记，如 `- [ ] AC-4 倒计时浮层不遮挡建筑（人工:建两个相邻建筑同屏过目）` | 用户 | 人工验收单 |

**light / heavy 不在起草期标注**：起草时无从预判验证成本，AC 的起草纪律也已经够重。分类由 agent **读验证口径（「验证」栏，省略时读声明本身）当场判**——需要起服务 / 多环境组合 / 点击流 → heavy，其余 → light；**判不准按 heavy 处理**（宁可 test 多跑一条，也不让 implement 起环境）。

manual 相反，**必须**在起草期标注：它回答的是「人能不能判」，不是「贵不贵」——agent 判不了的，跑多少次也判不了。

- **起草纪律**：能写成自动可验的绝不写成 manual（「导出正确」→「文件名为 X 且行数等于选中数」）；manual 项越少，用户验收负担越轻
- **勾选权分离**：
  - **auto-light** 的勾来自 implement 批末验证
  - **auto-heavy** 的勾**只来自 eo-test**——implement 批末遇到 heavy 项不跑、不勾、不代验，在汇报里列为「待 test」
  - **manual** 项 agent 不得自行判定勾选——用户确认方式 = 直接在人工验收单勾 checkbox（勾选权归用户，零打字），或走查中口头表态（agent 代勾须附确认记录）；change.md 的 manual 勾由 agent 依验收单同步（载体与规则见 [acceptance.md](acceptance.md)）
- **轻档 change（`tier: light`）**：auto AC 由 eo-implement 轻模式在实施前落成失败测试（AC 行回填「锁定：<测试锚点>」），测试绿即勾；**auto-heavy 出现即扩档信号**（轻档不起环境）；manual 项完成门用户当场过目，不生成验收单
- **未勾 ≠ 失败**：review 在 test 之前跑时，auto-heavy 项本就未勾——那是归属使然，不是缺陷
- **勾变脏即取消**：已勾的 AC 被后续修复影响 → 取消勾选并注明待复验（auto-heavy 注「待 test 复验」；manual 按 [acceptance.md](acceptance.md)「失效与重置」处理，含验收基线刷新）。**改过的代码上，旧的勾是假的**；影响范围判不清 → 全部取消

## 重验证的环境纪律

auto-heavy 的定义就是「要起环境」，所以环境政策落在这里：

- **环境是共享资源，agent 不拥有它的生命周期**：假定已就绪 → **先探测复用，不主动停**（用完留给下一个动作），只在需要换环境组合时重启
- **按环境组合分组跑**：一次起环境跑完该组合下的全部验证点，不为单条 AC 反复起停
- **「不停」的前提是重验证已收敛到单一阶段**（eo-test）——环境单主时「不停」才安全。多个 agent 并行争抢同一环境时它不成立，那种情况下先做归属分流，不要先动环境策略
- **起停命令与单次代价是项目特异知识**，不写进任何通用 skill：由项目侧记成 lesson（`trigger` 写「涉及起服务 / E2E 验证时」），经 eo-implement / eo-test / eo-fix 的 lessons 消费步骤（[lessons.md](lessons.md) §1）自动送达

## 撰写规则

- **用户视角**：描述用户能做到什么 / 观察到什么，不描述内部实现。
- **可独立验证**：每条一个可勾选项，从声明 + 验证栏能读出怎么操作、看什么结果。**验证栏走增量制**：只写声明本身读不出来的信息（操作入口、观察位置、构造条件）；声明已含触发条件与可观察结果的（如「当 X 失败时，用户看到 Y」），验证栏省略——同一行为不换个说法写两遍。
- **技术无关且可度量**：
  - ✅ 正例：「用户 3 步内完成导出，文件名为 `<项目名>-<日期>.zip`」
  - ❌ 反例：「API 200ms 内返回」「导出功能正常工作」（主观词 / 纯技术口径）
- **覆盖异常路径**：至少 1 条 AC 声明失败/边界时用户看到什么。
- **条数不模板化**：AC 数量由行为面（正常/异常/边界的实际数量）决定，随变更复杂度浮动——简单变更 2 条不嫌少，复杂变更 10 条不嫌多；禁止照模板示例凑固定条数（竞品教训：不看复杂度恒定摊派条数是「模板化输出」被诟病的根因）。
- **复杂行为可附 GWT**：Given/When/Then 场景作为该条 AC 的补充说明，不强制。

## 格式

```markdown
## 2. 验收清单
- [ ] AC-1 <用户能……>（验证：<声明读不出来的操作入口 / 观察位置>）
- [ ] AC-2 <当……失败时，用户看到……>          <!-- 声明已含触发与观察，验证栏省略 -->
```

## 时序纪律

**AC 先于 TODO 产出**（验收驱动）。TODO 拆解必须逐条映射到 AC（每条 TODO 标注「对应 AC-x」）；出现无法映射到任何 AC 的 TODO，说明要么 AC 漏了、要么 TODO 越界了。

## 生命周期

- 起草期由 eo-change 产出，用户确认后随 change 一起钉定。
- implement / review 期间发现 AC 写漏且 change 未归档 → 就地补 AC（Update preserves context）。
- 归档后 AC 冻结，成为该 change 的历史验收记录。
