# 验收清单（AC）规范（单一来源）

> 被 eo-change / eo-implement / eo-test / eo-review / eo-fix / eo-archive 引用。AC 是验收驱动的核心工件：**AC 就是「期望行为」的唯一声明**，口吻是「完成后我应该看到什么」——文档第一受众是用户，不是 implementer。

## 三重身份

1. **eo-implement 的完成判据**：TODO 全勾 + 自动 AC 自验通过 = 实施完成
2. **eo-archive 的验收门**：逐条核对证据或豁免（唯一硬门）
3. **eo-fix 取证时的最优书面证据**：语义分歧取证的证据瀑布（用户口述 > AC > state 意图佐证 > git 归属）中，AC 是书面期望的第一来源——但不是必要条件，无 AC 覆盖的行为按瀑布降级取证

## 行格式：一条 AC 三要素

每条 AC = **看到什么**（演示脚本口吻）+ **谁验**（归属标注）+ **不通过怎么办**（阻塞标注）：

```markdown
- [ ] AC-1 [自动·阻塞] 打开导出对话框选中多条，点导出后得到 `<项目名>-<日期>.zip`，行数等于选中数
- [ ] AC-2 [自动·阻塞] 当选中数为 0 时点导出，看到「请先选择条目」提示且不产生文件
- [ ] AC-3 [人工·非阻塞] 倒计时浮层不遮挡建筑（人工:建两个相邻建筑同屏过目）
```

- **归属两级**：
  - `[自动]`：agent 可判（跑命令、看输出、起环境点一遍都算）。默认归 eo-implement 批末自验勾选；change 挂了 /eo-test 闸门时由 test 验后勾选
  - `[人工]`：只有人能判（观感、手感、文案语感），以 `人工:` 标注验证方式。勾选权归用户，载体是验收单（[acceptance.md](acceptance.md)）
- **阻塞标注**：缺省即阻塞，可只标 `[自动]`；非阻塞显式写 `·非阻塞`。阻塞项不通过 → 禁止归档，回 implement 修复或回炉；非阻塞项不通过 → 记 backlog 可继续
- **验证栏增量制**：声明已含触发条件与可观察结果的（如 AC-2），不另写验证方式；只写声明读不出来的操作入口 / 观察位置 / 构造条件

## 起草纪律

- **用户视角**：描述用户能做到什么 / 观察到什么，不描述内部实现
- **可独立验证**：每条一个可勾选项，从声明 + 验证栏能读出怎么操作、看什么结果
- **技术无关且可度量**：
  - ✅ 正例：「用户 3 步内完成导出，文件名为 `<项目名>-<日期>.zip`」
  - ❌ 反例：「API 200ms 内返回」「导出功能正常工作」（主观词 / 纯技术口径）
- **覆盖异常路径**：至少 1 条 AC 声明失败/边界时用户看到什么
- **条数不模板化**：数量由行为面决定——简单变更 2 条不嫌少，复杂变更 10 条不嫌多；禁止照模板凑固定条数
- **能自动验的绝不写成人工**（「导出正确」→「文件名为 X 且行数等于选中数」）；人工项越少，用户验收负担越轻
- **不镀金**：AC 只覆盖 §1 声明的意图——用户没要的健壮性/扩展性预留不得写成 AC；确有价值的加固记 backlog
- **复杂行为可附 GWT**：Given/When/Then 作该条补充说明，不强制

## 勾选与证据

- **自动项**：eo-implement 批末按验证口径执行，命令 + 关键输出留在对话速报即算证据；挂了 /eo-test 闸门的 change，由 test 的执行证据勾选
- **人工项**：agent 严禁代勾；用户在验收单勾「通过」即证据（规则见 [acceptance.md](acceptance.md)）。change.md 的人工勾由 agent 依验收单同步
- **勾变脏即取消**：已勾的 AC 被后续修复影响 → 取消勾选并注明待复验（人工项按 [acceptance.md](acceptance.md)「失效与重置」处理）。改过的代码上，旧的勾是假的；影响范围判不清 → 全部取消

## 起环境的纪律

自动项需要起服务 / 多环境组合 / 点击流时：

- **环境是共享资源，agent 不拥有它的生命周期**：假定已就绪 → 先探测复用、不主动停，只在需要换环境组合时重启
- **按环境组合分组跑**：一次起环境跑完该组合下的全部验证点，不为单条 AC 反复起停
- **起停命令与单次代价是项目特异知识**：由项目侧记成 lesson（trigger 写「涉及起服务 / E2E 验证时」），经 lessons 消费步骤（[lessons.md](lessons.md) §1）送达

## 时序纪律

**AC 先于 TODO 产出**（验收驱动）。TODO 拆解必须逐条映射到 AC；出现无法映射到任何 AC 的 TODO，说明要么 AC 漏了、要么 TODO 越界了。

## 生命周期

- 起草期由 eo-change 产出，探针对齐（用户对话确认）后钉定
- implement / 闸门运行期间发现 AC 写漏且 change 未归档 → 确认后就地补（意图不变的精化）
- 归档后 AC 冻结，成为该 change 的历史验收记录
