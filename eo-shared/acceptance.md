# 人工验收单（acceptance.md）规范（单一来源）

> 被 eo-implement / eo-review / eo-archive / eo-fix 引用。体系中唯一以**「正在验收的人」为受众**的工件：AC 的 manual 项声明「验什么」，验收单负责「怎么验」。验收步骤是**实现的产物**——入口、路径、数据只有代码写完才确定，所以由 implement 生成，而不是起草期写进 AC。

## 何时存在

- change 的 AC 含 **manual 项**（「人工:」标记，见 [ac-spec.md](ac-spec.md)）→ eo-implement 全部 TODO 完成时生成；**无 manual 项不生成**（不打扰原则）
- 位置：`eo-doc/changes/<change-id>/acceptance.md`，随 change 归档冻结为验收记录

## 模板

**核心体验：用户拿到单子只需逐项勾选，零打字**；只有不通过/豁免才写一句话。

```markdown
# 验收单 — <change 标题>

> 验收基线：<最近一次影响人工项的 commit 短哈希>（implement 每次生成/更新时刷新）

## 这次改了什么
<≤3 句人话，说用户可感知的变化；不复读 AC、不讲实现>

## 环境准备
<怎么启动 / 需要什么数据或账号；无需准备写「无」>

## 逐项验收（人工项 N 条，验完勾「通过」即可）

### 1. <验什么，一句话>（AC-x）
- 操作：1) <打开哪里> 2) <做什么> 3) <…>
- 预期：<看到什么才算过>
- [ ] 通过

### 2. …

<!-- 某项有异常时在其「通过」行下加一行：`不通过：<哪里不对>` 或 `豁免：<原因>`（豁免同步记 change §8）；勾与异常行互斥 -->

## 已自动验证
<写实际证据：test.md 存在 →「其余 M 条已由 eo-test 验证，见 test.md」；不存在 →「其余 M 条中 <L> 条已按批末轻验证通过（<一句摘要>）；<H> 条重验证项尚未跑（本 change 未跑 eo-test）」。**未跑就写未跑**，不得把 auto-heavy 项含糊成「已验证」>

---
对我说「带我验收」，我按本单逐项带你走：起环境、指路，你只逐项表态。
```

仅 1 条人工项时可压缩为四行（入口、操作+预期、勾选行、自动证据），字段语义不变。

## 勾选与证据规则（硬性）

- **验收单的 checkbox 勾选权归用户**：用户在文件里勾「通过」这个动作本身就是确认证据，无需附加文字
- agent **严禁代勾**验收单。唯一例外：引导走查中用户口头表态后代勾，且必须在该项后追加确认记录 `（用户确认 <日期>「<原话一句>」）`——无确认记录的 agent 勾视为违规、按未勾处理
- change.md 里 manual AC 的勾由 agent 依据验收单**同步**（验收单是人工项状态的信源）
- 用户任何时刻可提前验收——勾了即生效，不必等归档

## 失效与重置（硬性）

以下事件发生时，agent 取消受影响人工项的勾选（验收单与 change.md 两处）、在该项下注明一行重置原因、刷新验收基线；影响范围判不清 → 全部重置：

- 修复循环（implement 模式二）改变了某人工项的入口/行为
- eo-fix 的改动落在某未归档 change 的人工项行为上（落点记账时处理）
- manual AC 集合变化（新增 / 改写 / auto↔manual 转换）→ 同步增删对应验收项，新增项为未勾

## 生命周期（软前门 / 唯一硬门）

| 环节 | 责任 |
|------|------|
| eo-implement 全部完成 | 生成初版（操作步骤写实现后才确定的入口/路径/数据）；速报只给路径 + 人工项一览，**不阻塞等待表态** |
| eo-implement 模式二（修复循环） | 按「失效与重置」处理受影响项；验收单出现「不通过：」行即为修复循环的正式输入 |
| eo-review 通过（无 P0/P1） | 速报提示可人工验收（测试状态如实标注：已过 / 未跑 eo-test） |
| eo-archive（**唯一硬门**） | 从 change.md §2 解析 manual 集合 → 非空则验收单必须存在且**一一对应**（缺项/孤儿/重复 = 校验失败）；核对勾选与异常行（agent 代勾须有确认记录）；验收基线之后存在影响人工项的提交 → 受影响项按未勾；**未勾的 auto-heavy AC 一并过此门**（跳过 eo-test 时它们必然未勾，勾选权归 test 不归 implement）；**归档前把已勾项汇总一句请用户一键确认**（封闭选择，作为跨会话最终复核）；不通过/未勾项 → 三选一（补齐：回 implement 修复或 test 补验 / 显式豁免 / 终止归档） |

「不通过」走回修时：status 由 `reviewed` 置回 `implementing`（implement 执行）。修复提交必须重新 Review；是否重走 Test 按 [conventions.md](conventions.md) §3 的测试证据处置判定——既有证据可沿用则跳过，失效则定向或完整复验。若同时存在未核销 Test FAIL，先回原 tester 复验，不得走沿用分支。

## 引导走查（可选模式）

用户说「带我验收」或等价表述：

1. **定位验收单**：用户点名 change-id 优先；唯一候选（仅一个未归档 change 有验收单）自动选中；多候选列出请选；无候选说明原因并引导（如 implement 尚未完成）
2. 按「环境准备」起环境，逐项：给出操作与预期 → 等用户一项一个表态 → 通过则代勾并附确认记录，异常则写「不通过：/豁免：」行，同步 change.md 的 manual 勾
3. 可中途暂停——进度在单上，随时续
4. 「不通过」→ 记录用户反馈原话，走查结束后按修复循环处理
