# 目标契约（跨阶段共享语义）

> 目标：让模糊意图在进入交付前可判断、可约束、可验证，同时不制造第二份真相源。

## 使用原则

七维是 Agent 内部维护的 **coverage lens（覆盖镜头）**，不是强制七问、七段模板或逐项打勾的表单。先从现有对话与工件中提取答案，只在某个缺口会实质改变方向、范围或裁决时才向用户追问；无关维度可以不渲染。

同一维度会经过「上游生产 → change 冻结 → 下游消费/验证」。后续阶段不得静默改写上游已经冻结的 Why、Outcome、Bounds 或 Trade；发现冲突时回到用户决策或 change revision。

## 七维投影

| 原始维度 | EO 表达 | 要回答的问题 |
|---------|---------|-------------|
| Why | Why | 为谁解决什么问题，为什么值得现在做？ |
| Done | Outcome | 成功后的外部可观察状态是什么？哪些信号支持继续或停止？ |
| Proof | Evidence | 当前方向依据什么成立，后续要由什么证据完成证明？ |
| Anti | False Success | 怎样会出现「表面成功，实际背离 Why」？ |
| Bounds | Bounds | 第一版做什么、不做什么，哪些红线和前置条件不可越过？ |
| Trade | Trade | 主动得到什么、放弃什么，优先级和翻案条件是什么？ |
| Unknown | Unknown | 哪些未知仍会影响结论，由谁、何时、用什么方式消解？ |

名称只是面向阶段的投影，不要求所有工件使用同一组标题。

## Proof 的三层边界

1. **决策依据**：证明问题、前提或方向选择目前可信。由 brainstorming 的现状核验和有界调研产生，必须说明它能影响哪项决策。
2. **证明义务**：定义交付后必须由哪些可观察结果证明成功。由 brainstorming 起草成功信号，进入 change 后编译并冻结为 AC、负向约束或人工门。
3. **交付证据**：证明当前实现确实履行了证明义务。只能由 implement、test、review、manual 等交付阶段基于当前工件产生。

上游的资料、推理或成功信号不是交付证据。Brainstorming 不得据此宣告实现 PASS；Loop 也不得用 worker 自述替代独立证据。

独立性服从现有节点分工：implement 的自检可以在 `ac-spec.md` 允许的范围内作为 auto-light 证据，但不能冒充本应由 test、review 或用户产生的独立证据。Loop 只核角色、工件、基线与证据归属，不亲自补做验证。

## 阶段权责

下表定义跨阶段的目标权责，不代表每个 skill 都已增加专项检查；当前是否执行本规范，以对应 skill 正文是否引用本文件为准。未接入的阶段是后续审计挂点，不得据表宣称已有检查已经运行。

| 阶段 | 生产或处理 | 不得越界 |
|------|-----------|---------|
| brainstorming | Why、方向级 Outcome、决策依据、成功信号、False Success、产品 Bounds、价值 Trade、已知 Unknown 的分流 | 不写实现级步骤，不宣告交付 PASS |
| change | 将已钉方向冻结为意图、AC、TODO、风险与开放问题 | 不静默重做已钉的产品决策 |
| change-review | 审计目标与取舍是否缺失、矛盾、不可验证 | 不替用户决定产品/价值取舍 |
| loop | 消费冻结目标，编译当轮出口、运行边界、证据门和升级策略 | 不临场降低 AC、改写 Why 或移动判定标准 |
| implement / test / review / manual | 产生或独立验证交付证据 | 不用修改判据、测试或口径来换取绿灯 |

## Trade 的默认裁决顺序

没有更明确授权时，按以下顺序处理冲突：

1. 安全、权限、人工门、熔断等硬约束
2. 已冻结的 Why、Bounds 与 AC
3. 判定和证据完整性
4. 最小改动与可逆性
5. 速度、成本与并行效率

前三层不能由 review 或 loop 临场牺牲；需要越过时，回到用户决策或 change revision。

用户本轮授权可以收紧运行边界、预算或资源使用，但不能绕过 change revision 覆盖已冻结的 Why、Bounds 或 AC。

## Unknown 分流

- **A 类（可自治）**：局部、可逆，且不改变 Why、AC、范围、架构、外部契约、数据、权限、预算或人工门。执行者可先做后报，记录选择、理由和回退方式。
- **B 类（分支决策门）**：仍在已冻结目标与硬约束内，但选择不够局部、可逆，且会改变某个实施分支；其他独立工作仍可继续。暂停受影响分支，合并成封闭选择交给用户。
- **C 类（硬决策门）**：会改变 Why、产品方向、范围、AC、架构、外部契约、数据、权限、预算、人工门或其他硬约束，或涉及不可逆动作。变更前必须停止并取得用户裁决。
- **证据未知**：允许一次有界探测；仍取不到必要证据时只能标未验证或阻塞，不得写 PASS。

只有 A 类允许先做后报；B / C 类必须在变更前进入决策门。Brainstorming 负责提前识别并路由已知 Unknown；Loop 负责治理执行中涌现的 Unknown。Handoff 只搬运已知状态，不能代替权限与升级规则。
