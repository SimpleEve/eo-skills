# 粒度规范：硬指标、trivial 判据、拆分决策表、三档判档、并行拆解（单一来源）

> 被 eo-change / eo-fix / eo-change-review / eo-implement / eo-loop 引用。目标：「一个 change 只做一件事」从软规则变成可校验的数字。三档判档见 §5，并行拆解见 §6。

## 1. change 粒度硬指标（采用 spec-kitty 数值，试运行；适用全档）

| 指标 | 理想 | 硬上限 | 超限动作 |
|------|------|--------|---------|
| TODO 数 | 3-7 | 10 | **必须**拆 change 序列 |
| change.md 全文 | 200-500 行 | 700 行 | **必须**拆 change 序列 |

- 校验时机：eo-change 收尾自检（`wc -l` + 数 TODO），超软标建议拆、超硬标**拒绝确认**；eo-change-review 复查同项。
- 量化理由（spec-kitty 原文）：超过 700 行 agent 会丢细节、跳步骤；200-500 行恰好装下全部上下文。
- 拆分方式：按 AC 分组切成序列，第一个 = MVP，其余排入 changes/INDEX.md 队列或 backlog。

## 2. trivial 硬判据（直改模式短路）

**同时满足**以下四条 → 不开 change，走直改模式（改完常规 commit，随下次任意 doc-manager sync 顺带收割——注意 sync 无自动触发）：

1. 不改变用户可见的**功能语义与交互逻辑**（纯外观/样式、文案、多语言、重命名、格式化、显而易见的小 bug 修复都算 trivial）；
2. 不改对外接口、不动持久化数据结构；
3. **无需方案权衡**——不产生值得记录的技术决策（一旦要做选型或权衡，就有了开 change 的理由）；
4. 单次会话可完成。

**描述成本下界**（低风险 tie-breaker，**非独立充分条件**）：在已满足上方第 2/3 条（不改对外接口与持久化结构、无方案权衡）且误解代价低的前提下，说清怎么改所需的字数 ≈ 直接改掉的成本 → 直改。触碰对外接口 / 持久化结构 / 不可逆操作的改动，无论描述多短都不得走此下界。

任何一条不满足 → 升级 change 模式。**文件数不设限**：按需求性质判定——多语言、全局样式调整可涉及几十个文件仍是 trivial；反之 3 个文件的逻辑重构也不是。文件数只作提示信号（量大且非机械同质时确认一句）。

直改护栏：UI 直改仍受 DESIGN.md 约束（改前读）；commit 建议带 `fix:` / `ui:` 前缀（见 conventions.md）；直改本身零工件——够格开工件的走轻档 change（§5）。

## 3. 更新 vs 新开决策表（借 OpenSpec）

> **"Update preserves context. New change provides clarity."**

| 情形 | 动作 |
|------|------|
| 意图相同的精化：发现边缘情况、方法微调、范围缩到 MVP | **就地更新**本 change |
| 意图本质变化 / 与原范围重叠 <50% / 原 change 可独立收尾 | **新开 change** |

## 4. TODO 质量底线

- 每条 TODO 三要素：描述 / 涉及文件 / 对应 AC。
- **勾选双层语义**（统一口径，全 skill 一致）：TODO 勾 = 代码落地（编译/lint/相关单测绿）；AC 勾 = 验收通过（批末按验证口径执行）。两层分离——TODO 全勾不代表 AC 已验。
- **完成判据是条件要素**：仅当多条 TODO 对应同一条 AC（单条完成 ≠ 该 AC 可验）时逐条写，作为该 TODO 的额外勾选门；一对一映射不写。验证信息只在 AC 层写一遍，不在 TODO 层复述。
- **禁止占位符**：出现「补充错误处理」「后续完善」「implement later」这类词即判定拆解失败，必须写实。
- 按 Batch 分组，Batch 1 = MVP，批间可独立验证对应 AC（STOP and VALIDATE）；互不干扰的批可标并行组（见 §6）。

## 5. 三档判档决策表（trivial 之上：轻档 vs 全档）

判档权在 agent：按本表判档并一句话宣告（含该档取舍），用户一个词可改档。输入源（口述 / backlog 卡 / 外部 GitHub issue / brainstorming 捕获）与档位正交，统一过本表。

1. 满足 §2 trivial 判据（含其安全前提下的描述成本下界）→ **直改**
2. 以下四问**任一为「是」→ 全档**，全「否」→ **轻档**（`tier: light`，模板见 eo-change/references/change-template.md）：
   - **影响面圈不住**？（跨模块边界 / 动共享不变量 / 改对外接口或持久化结构）
   - **需要多方共同设计/实施**？（多个共同所有者需要事前共享同一份理解并持续协同——**不含**单执行者 + 完成门的独立复核者）
   - **本次会话明显收不了口**？（上下文余量或剩余工作量可见地超出当前会话——按当下可观测信号判，不做远期预测）
   - **误解代价高**？（agent 理解偏了会造成难逆损失，或返工远贵于澄清）

两条形式原则：

- **判不准默认低档**，升档靠**事后信号**而非事前估计——扩档信号：实施中发现影响面圈不住 / agent 两次以上跑偏 / AC 超 5 条装不下 / 出现 auto-heavy 验证需求 / manual 项超过 2 条。扩档动作见 eo-implement 轻模式。
- **判界写相对量**（影响面能否圈住、可审查性），不写死行数阈值——绝对数字会随模型能力上移而过时。文件数/行数只作提示信号。

## 6. 并行拆解：互不干扰判据与并行组（供 eo-change 拆批、eo-implement 执行、eo-loop 派发消费）

并行的前提不是画依赖图，而是**互不干扰**——拆得好多路齐头并进，拆得不好互相改对方的代码。判不准 → 不并行；**串行永远是安全缺省**。

**互不干扰判据**（两条同时满足才可并行）：

1. **文件集不相交**：两批 TODO 文件栏的并集无交集（机械可判——文件栏的第二用途）
2. **无逻辑依赖**：一批不消费另一批产出的接口 / 数据结构 / 生成物（生产者-消费者关系即依赖，文件不相交也不得并行）

**并行组标注**（change.md §3）：Batch 号加字母后缀表示同层并行组——`Batch 2a` / `Batch 2b` 互不干扰、可并行；**纯数字批 = 串行**（存量 change 零迁移）。层间仍串行：同层全部收口并过合流 checkpoint 后才进下一层。

**机械校验（并行派发方责任，成本 ≈ 0）**：并行派发前必查同层各批文件集两两不相交；相交 → 拒绝并行、降级串行并一句话报告。标注写错**只阻塞并行、不阻塞实施**——串行执行同层批照常合法。

**现场隔离与合流**：跨 worker 并行执行时**一 worker 一独立 worktree**（分支管路线、worktree 管现场；具体手段归 eo-loop 基底文件）。同层全部收口后跑**合流 checkpoint**：合并结果上的常规绿灯（编译 / lint / 既有测试）+ 该层各批对应 AC 复核；冲突修复派回引入冲突的批的执行者。单会话串行执行同层批时无需隔离，层末合流 checkpoint 照跑（退化为该层 AC 验证的汇总）。

**change 序列并行**（§1 超标拆序列时顺手判）：后续 change 之间意图独立且预计文件面不相交 → 在 changes/INDEX.md 摘要列附注「可与 #N 并行」，供 eo-loop 圈并行收敛组消费；判不准不标。

**地基优先**：修测试 / 补 CI / 删死代码 / 依赖加固类地基工作天然互不干扰，优先拆成可并行批——地基越稳，可安全并行的幅度越大。
