# 深挖模式方法论（系统化根因调查）

> 仅在 eo-fix 升级深挖模式时加载。原则：**一次只验一个假设；每一步产生可记录的证据；结束必还原现场。**

## 阶段一：固定复现

没有稳定复现之前，不做任何假设验证。

1. **最小化复现**：从用户的复现步骤出发，逐步删减无关操作/数据，得到最短路径
2. **确定性检查**：连续跑 ≥3 次确认稳定；不稳定则先找「让它稳定」的条件（特定数据、时序、并发、环境变量）——间歇性本身就是重要线索（指向竞态/缓存/外部状态）
3. **记录环境**：commit hash、运行环境、配置、数据形态，写入调查记录
4. 实在无法稳定复现 → 加持久化日志埋点等下一次发生，向用户说明并暂停（不硬猜）

## 阶段二：假设清单

1. **分层列举**可能原因（不带偏好地列全）：输入/数据层、业务逻辑层、状态/缓存层、并发/时序、外部依赖、环境/配置
2. 结合三方对比结论与 lessons 检索结果标注每条的**先验概率**（高/中/低）
3. 按 `概率 × 验证成本` 排序：便宜且可能性高的先验

## 阶段三：二分排除

按排序逐条验证，**一次只动一个变量**：

| 手段 | 适用 |
|------|------|
| `git bisect` | 「以前是好的」类问题，定位引入 commit（用阶段一的复现脚本作判据） |
| 代码路径二分 | 在调用链中点插桩，判断问题在前半还是后半，递归缩小 |
| 数据二分 | 换最小数据集/对照数据，区分数据问题 vs 逻辑问题 |
| 插桩观察 | 关键状态打日志（带唯一前缀如 `[EOFIX]`，便于结束后一键清除） |
| 环境对照 | 干净环境重跑，区分环境问题 vs 代码问题 |

每次验证后在调查记录里写：假设 → 手段 → 观察 → 结论（排除/确认/存疑）。**假设被排除同样记录**——防止绕圈重验。

## 阶段四：验证与还原

1. **根因确认标准**：能解释**全部**观察到的现象（不是部分）+ 据它可预测「改 X 则 Y」并验证命中。只满足一半 → 回阶段二补假设
2. 回 eo-fix 第四步路由表定归属，执行修复
3. **修复验证**：阶段一的最小复现转为回归验证跑通；插桩期间发现的相邻可疑点如实上报（不顺手修）
4. **还原现场**：清除全部 `[EOFIX]` 插桩与临时日志；`git bisect reset`；恢复被改动的配置。`git status` 确认除修复本身外无残留
5. 调查记录收尾：根因一句话 + 证据链摘要；有普适教训 → 提议 /eo-project-record

## 调查记录模板（tmp/eo/fix/<date>-<slug>.md）

```markdown
# <bug 一句话> — 调查记录
- 日期 / commit / 环境：...
- 复现：<最小步骤>（稳定性：N/N）

## 假设与验证
| # | 假设 | 手段 | 观察 | 结论 |
|---|------|------|------|------|

## 根因
<一句话> + 证据链摘要

## 修复与还原
- 修复：<file:line 简述>；回归验证：通过
- 还原核对：插桩清除 ✓ / bisect reset ✓ / git status 干净 ✓
```
